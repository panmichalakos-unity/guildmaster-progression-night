## ADR-0005 · 2026-07-07 · v1 core schema decisions (M0-003, `0001_init.sql`)

**Decision:** Translated the v1 Prototype Spine (data-model v0.8) into `data/migrations/0001_init.sql` — 50 game tables + `schema_migration` bookkeeping. Physical names are `lower_snake_case` (SQLite matches identifiers case-insensitively, so doc-style `UPPER_CASE` queries still work). Seed/content tables carry immutable `slug` + renameable `display_name` (naming-bible convention); runtime entities use integer ids.

**Deliberate deviations from the literal spine list** (each cross-validated against the system docs):
1. **`pull_consumable` added** — omitted from the spine's in-v1 list but required by G7/G12 (readiness review) and the raid-prep v1 consumable plan; M7-003 depends on it.
2. **`synergy_tag` + `spec_synergy_tag` added** — spine says defer, but backlog M1 DoD ("utilities + synergy tags"), the v1 content table ("~5 synergy tags"), and the naming bible (5 named tags) all put them in v1. Spine is the outlier.
3. **`week_action.action_type_id` added** — the ERD draws `ACTION_TYPE → WEEK_ACTION` (v0.7) but the older v0.4 column list predates it.
4. **`loot_item.slot` → `slot_id` FK** to `slot` (relational 7-slot model), and **`loot_item.encounter_id` nullable** — Marks-vendor gear and generated starting gear (M2-003) don't drop from bosses.
5. **`schema_migration` table** instead of `GAME_STATE.schema_version` (stack-doc sketch) — `game_state` has no row until genesis, so a migrated-but-empty DB needs trackable state. M0-004 records applied filenames here.

**Structural constraints downstream code can rely on:** one active avatar per player (partial unique index); `game_state` singleton (`CHECK game_id = 1`); one scheduled event per (week, day, time_slot); `raid_assignment` PK includes `assignment_type` (an avatar can hold interrupt duty AND a consumable plan); `pull.attempt_number` unique per (event, encounter); `performance_rating` CHECK 1–10; `relationship` bans self-reference.

**Enum spellings the M1/M5 seeds and services MUST match (CHECKed in schema):** time slots `afternoon/evening/late` · event types `raid/dungeon/rest/social` · lanes `gearing/development/supply/people/rest` · assignment types `tank/heal_focus/interrupt/soak/cooldown/consumables` · loot systems `council/dkp/roll` · policies `guild_funded/subsidized/byo`, `mandatory/suggested/voluntary`, `guild_covered/not_covered` · involvement `manual/assisted/instant` · membership status `applicant/trial/member/former` · objective results `exceeded/met/missed/failed` · target selectors `tank/healer/melee/ranged/random/assigned` · ledger txn types `donation/proceeds/farming/provision/repair/purchase/conversion`. Extending any enum = a new numbered migration, not an ad-hoc edit.

**Consequences:** M0-004 must run `PRAGMA foreign_keys = ON` per connection and wrap migrations in transactions. Deferred v1.1 tables (`quirk`, `player_quirk`, `avatar_resistance`, `drama_event`) arrive as new migrations in M10/M11; `relationship` ships now but is write-only until M10.

## ADR-0006 · 2026-07-08 · Migration service pattern + a dev-machine caveat (M0-004)

**Decision:** `sim/db/migrator.gd` (pure static `Migrator`, no scene-tree deps) owns DB opening and migrations: idempotent extension guard → open with `foreign_keys` ON → apply pending `data/migrations/*.sql` in filename order, one transaction per file, recording filenames in `schema_migration`. Failures name the offending file and roll back. Headless smoke: `godot --headless -s tools/smoke/migrate_smoke.gd`. Probed godot-sqlite v4.7 facts the design relies on: `query()` executes multi-statement scripts; `error_message` carries the SQLite error; the `foreign_keys` property works. **Convention: migration files must not contain their own BEGIN/COMMIT** (the runner owns transactions).

**Dev-machine caveat — ROOT CAUSE FOUND & FIXED (2026-07-08):** `godot --headless --quit` hung on *any* project because the CLI shim pointed at the **Steam build** of Godot: launching that exe directly bounces through the Steam launcher, which pops a "how do you want to open Godot" launch-option dialog — invisible and unanswerable in headless runs, so the process waits forever. (Diagnosed by elimination: pristine copies and a brand-new minimal project hung; `-s`/`--import` modes worked; Panos observed the popup interactively.)
**Fix:** `~/.local/bin/godot` now points at the **official pinned `Godot_v4.7-stable_win64_console.exe`** (installed at `~/.local/godot-4.7/`, console build for reliable CLI pipes; Steam shim backed up as `godot.steam.bak`). Same engine commit as the Steam build (`5b4e0cb0f`) — full version/determinism parity. The Steam editor remains fine for interactive use; all CLI/CI-style verification uses the official binary. Full battery re-verified on it: `--quit` exits cleanly, GdUnit 9/9, migration smoke PASS.

**Second mechanism found (2026-07-08, M0-006):** even on the official binary, **project-run mode (`--headless --quit`) hangs while a Godot editor has the project open and busy** (fresh editor session importing/holding the project); `-s` script mode, `--import`, GdUnit, and all smokes are unaffected. Local rule: run `-s`-based smokes freely; run `godot --headless --quit` only with the editor closed (CI containers have no editor and are unaffected). Once M4-001 adds a main scene, the `--quit` smoke gains real value — revisit then.

## ADR-0007 · 2026-07-08 · Seed format: CSV rows + JSON manifest, slug refs, true upserts (M0-005)

**Decision:** Seeds are **CSV files (one per table)** listed by **`data/seeds/manifest.json` in dependency order**, loaded by `sim/db/seed_loader.gd` in a single all-or-nothing transaction. Full convention in `data/seeds/README.md`.
- **Slug natural keys everywhere; seed files never carry integer ids.** FK columns are authored as `*_slug`; the manifest's `refs` entries declare the resolution (`{"column": "class_slug", "table": "class", "as": "class_id"}`), which also covers FK names that differ from the ref table (`utility_slug` → `raid_utility` → `utility_id`). Bridge tables declare `"key": [...]` for their composite upsert key.
- **True UPSERT (`ON CONFLICT ... DO UPDATE/DO NOTHING`), never `INSERT OR REPLACE`** — reloads are idempotent and integer PKs stay stable, so FKs written by earlier loads never dangle.
- **Types come from the schema** (`pragma_table_info` coercion; empty cell → NULL), so CSV needs no type annotations and Python checks (M0-006) can validate the same way.
- Structural seeds shipped now: `role.csv` (4 roles), `slot.csv` (7 gear slots) — fixed by the design docs, needed by M1 anyway.

**Why CSV+JSON:** dbt-seed idiom (git-diffable rows), `FileAccess.get_csv_line()` built in, trivial for `seed_check.py`; the manifest needs nesting → JSON.
**Consequences:** M1 tasks fill this format in (no parallel formats). Known M1-002 decision point: `encounter_event` → phase refs need either a `slug` on `encounter_phase` via a new migration (preferred) or composite-key ref support — decide there. Loader distinguishes "ref table empty" (per-row unknown-slug error) from "ref table missing/no slug column" (structural error).

## ADR-0012 · 2026-07-08 · RngStream: named hierarchical streams + the GlobalScope shadow trap (M2-001)

**Decision:** `sim/rng/rng_stream.gd` (`RngStream`) is THE one RNG pattern for sim code. Named streams derive from the master seed (`RngStream.derive(seed, "roster_gen")`) via our own **FNV-1a 64** (not `String.hash()` — derived seeds can never shift under an engine upgrade); `substream("traits")` forks hierarchically WITHOUT advancing the parent, so systems cannot perturb each other's sequences. Draw API: `randi_range/randf/randf_range/randfn/pick/weighted_pick/shuffle`, plus `draw_count` and `stream_path` for observability/repros. `tests/helpers/sim_fixture.gd` (`SimFixture`) is the sim test pattern: `new_campaign_db()` (migrated+seeded :memory:), `rng(name)` off `TEST_SEED`, run-twice-compare determinism proofs. Sim code must accept `(input_state, rng)` explicitly.

**Trap found & fixed (regression-guarded):** inside a GDScript class, an UNQUALIFIED call like `randf_range(...)` can bind to the **unseeded `@GlobalScope` function** instead of the class's own method — hidden global randomness inside the RNG class itself. Caught immediately by the lockstep determinism test (`draw_count` stayed 0 while sequences diverged). Rule: **inside RngStream, every internal draw is `self.`-qualified**; tests assert exact `draw_count` so a binding regression fails loudly. Sim code elsewhere always draws through a held stream object (`rng.randf()`), which is naturally qualified — but never name a sim function `randf`/`randi_range`/etc.

## ADR-0013 · 2026-07-08 · Roster generation: latent factors, not independent dice (M2-002)

**Decision:** `sim/roster/roster_gen.gd` (`RosterGen`) generates PLAYER rosters as a pure `(presets, count, rng) -> players` function. Anti-grey-goo model: every trait derives from **four latent factors + bounded noise** — `talent` (stratified star/core/fringe tiers so every roster has aces, a middle, and projects), `steadiness` (consistency/loyalty/coachability up; volatility/ego down), `drive` (growth/influence/ego up; burnout hotter), and `experience` (from the life preset: young_gun ≈25 vs veteran ≈80 — raises current skill/influence/loyalty, lowers potential headroom/growth/coachability). Life presets stamp availability windows + volatility/burnout/loyalty mods. `loyalty_current` starts AT `loyalty_baseline` (conventions Shape A anchor). Distribution parameters live in `tuning.json` `roster` (tiers, shares, experience map, preset weights); derivation coefficients are generator shape in code.
**Also:** `data/seeds/life_situation.csv` — the 6 canonical presets (single/student/working_parent/shift_worker/veteran/young_gun), which no M1 ticket owned; gated in seed_check ("exactly 6"). `sim/roster/name_gen.gd` (`NameGen`) — the naming bible's three weighted handle pools (root+suffix 55 / compound 30 / human-leak 15, collision → digit suffix). `sim/core/tuning.gd` (`Tuning`) — shared cached loader for tuning.json.
**Consequences:** M2-003 assigns avatars WITHOUT touching PLAYER semantics (strict boundary); M8-001 population tick reuses `RosterGen`+`NameGen` (do not fork). Correlation gates live in tests (execution↔awareness > 0.25 etc. over n=300) — retuning coefficients must keep them true or consciously change them.

## ADR-0014 · 2026-07-09 · Avatar assignment: role plan, template starter gear, additive gear_score (M2-003)

**Decision:** `sim/roster/avatar_gen.gd` (`AvatarGen`) assigns each player one active avatar. **Role plan** fills tuning `roster.role_targets` (4 tank / 7 healer / 8 melee / 9 ranged for 28 — a 20-lineup of 2–3T/5H/13D with bench depth on every axis), deterministically shuffled so role never correlates with roster order; spec picked uniformly among that role's seed specs. **Starter gear = 7 template rows** in `loot_item.csv` (`starter_*`, "Worn Helm"…, encounter NULL, marks 0) with the actual level on `avatar_item.item_level` — the denorm column carries per-avatar variance, zero generated-row pollution. **`gear_score` = SUM of equipped slot levels** — an upgrade's power delta is exactly its slot delta (the gear-doc contract M6-005 builds on); `avatar.item_level` = rounded average. ## ADR-0016 · 2026-07-09 · Pull resolver contract: dictionaries, named checks, legibility enforced (M3-001)

**Decision:** `sim/resolution/pull_contracts.gd` (`PullContracts`) defines THE resolver boundary: `PullResolver.resolve(input: Dictionary, rng: RngStream) -> Dictionary` (M3-002 implements). **PullInput** = encounter demands + phases + effective event placements (selector already COALESCEd) + per-participant snapshot (skill facets, gear, caps, state, assignments, consumables) + `encounter_progress` + attempt + tuning. **PullResult** keys map 1:1 onto the fact tables (`pull` → PULL incl. `wipe_reason`, `participants` → PULL_PARTICIPANT with `raw_contribution` + `performance_rating` 1–10, `events` → PULL_EVENT with unique `sequence_no` + `log_line`, `state_deltas` → GUILD_ENCOUNTER_PROGRESS + morale/fatigue/form deltas) **plus one derived surface: `checks[]`** ({check, margin, passed, detail} per the doc's checks catalogue) — the legible-failure record that `wipe_reason` and the M7-005 why-view derive from.
**Validators enforce the design pillars structurally:** a wipe without `wipe_reason` is INVALID ("legible failure is the engine"), a kill with one is invalid, kills must set `drops_loot`, ratings clamp 1–10, event sequence unique, every event's log_line non-empty ("the feed is the show").
**Fixtures:** `tests/helpers/pull_fixtures.gd` — five synthetic 20-raider shapes shared by all M3 tasks (clean_kill / mechanic_failure / dps_pressure / healing_pressure / tank_pressure — the last with deliberately non-uncrittable tanks). Plain Dictionaries over typed classes: matches the project's data style, serializes trivially for the harness, and keeps the boundary engine-agnostic.

## ADR-0017 · 2026-07-09 · Resolution core math: normalization, couplings, the gate (M3-002 / M3a)

**Decision:** `sim/resolution/contribution.gd` (stages 1+2) + `sim/resolution/checks.gd` (stage 3), pure over the M3-001 contracts. Interpretation choices where the doc is symbolic (all overridable via `input.tuning`, defaults mirrored in `tuning.json` `resolution`):
1. **Per-raider lane normalization** — lane output = sum of lane contributions / STARTING lane count, so authored demands (0–100 band) compare directly regardless of comp, while deaths still drag the lane (M3-003 re-aggregates via `exclude`).
2. **Contribution math** — ceiling = avg ilvl × 2.2 · skill = exec 0.5 + proficiency 0.25 + familiarity 0.25, spec_difficulty bites at 0.4 × the shortfall BELOW the skill line only (master shrugs, novice suffers) · realization = 0.35 + skill/100 × 0.6 · situational mods each clamped [0.85, 1.15], product [0.7, 1.3] · variance width = base × (1.5 − consistency/100).
3. **The healing coupling** — demand = healing_check × (1 + avoidable_pressure + tank_wear); avoidable_pressure = max(0, 55 − avg awareness) × rate; tank_wear from main-tank ilvl below par. A sloppy raid strains its healers (tested).
4. **The tank gate** — near-binary via the hard sigmoid (scale 12 vs 25) + a flat **uncrittable_gate_penalty (25)** on the margin when the MAIN tank (assignment target "main", else first tank) is not uncrittable.
5. **Culprit hints in every check detail** ("weakest: ranged_3 (31.0)") — wipe_reason (M3-004) and the why-view consume these.
**Fixture recalibration:** clean_kill moved to gear 260 / demands 20 — its original numbers produced margin ≈ +20, which on the hard curve is only p≈0.84, NOT the "over-geared → one-shot" saturation the doc demands. Fixtures must sit where their scenario claims.
**Consequences:** M3-003 timeline calls these lanes/checks (never duplicates math); M3-005 harness asserts the 60–80% band by sliding demands against a real roster.

## ADR-0018 · 2026-07-09 · Timeline engine + resolution recalibration (M3-003 / M3b)

**Decision:** `sim/resolution/timeline.gd` (`Timeline.run(input, rng)`) walks phases in order, fires each placed ENCOUNTER_EVENT (weight→fire count), and dispatches purely on the seed row's `effect_category` — `death` / `save` / `tension` / `surge` / `duty_check` / `tank_check` — with `target_selector` (tank/healer/melee/ranged/random/assigned) choosing among the LIVING. No boss-specific code; a new boss is new rows. Deaths remove bodies → the final lane re-aggregation (via `substream("contribution")` reused identically, ADR-0012) drops the fallen = cascade. Outcome = the M3-002 checks on survivors + death-collapse, and every wipe names the dominant failed check + culprit (`_WIPE_PRECEDENCE`: tank > collapse > dps > healing > mechanic). Data-driven behaviors: cascade_death only bites after a prior death; clutch_save cancels the phase's most recent death; assigned_duty failure kills a random raider (the unchecked add); the tank gate kills only a non-uncrittable main tank.

**Three real resolution flaws surfaced by the clean_kill=one-shot test (fixed at the source, not by weakening the test):**
1. **Sigmoid scales too wide to saturate** — soft 25 / hard 12 capped even a +40 margin at p≈0.83, so "over-geared → one-shot" was mathematically unreachable. Recalibrated to **soft 12 / hard 7**: matched content (margin≈0) stays a coin flip, but a strong positive margin now saturates (kill) and a strong negative one is decisive (wipe), exactly as the doc's difficulty-via-margin demands.
2. **Lane normalization erased comp as a decision** — dividing by ACTUAL lane size meant 3 healers produced the same HPS as 5. Now lanes divide by a fixed **`reference_comp` (2 tank / 5 healer / 13 dps)**, so thin healing genuinely hurts and stacking a lane genuinely helps.
3. **Tank survival ignored healing** — the doc lists tank-healing as a tank-check input. Added `tank_healing_share` (0.35 of HPS) to tank output, so a dead/thin healer lane drops tanks too.
Also fixed: the M3-001 fixtures carried `effect_category="fixture"` (placeholder) and so drove nothing — mapped event_type_slug → real category/roll_attribute mirroring event_type.csv.

**Consequences:** all resolution constants live in `tuning.json` `resolution`; the M3-005 harness will find the gear level where margin≈0 and assert the 60–80% band there. M3-004 assembles the full PullResult (ratings + learning arc + state writes) on top of `Timeline.run`.

## ADR-0019 · 2026-07-10 · Ratings, the gated learning arc, state deltas, resolver assembly (M3-004 / M3c)

**Decision:** `sim/resolution/rating.gd` + `sim/resolution/pull_resolver.gd` complete the engine.
1. **Ratings are relative:** expected = ceiling × 0.65 (a plain 50-skill raider on that gear); rating = clamp(5.5 + (actual/expected − 1) × 12 + event deltas, 1..10). The night's STORY moves the number: avoidable death −2, missed duty −2, clutch save +1.5, clean duty/surge/near-death-survived +0.5. `raw_contribution` (×10, int) rides alongside for logs/MVP.
2. **The learning arc runs both directions.** Forward: progress bumps familiarity (skill_realization's 25% input) and SHAVES event severity (`severity_learning_rate` in Timeline) — the raid that has seen the fire stands in it less. Back: kill → 100; wipe gain = per-attempt gain × closeness, gated on the **blocking margin — the WORST failed check** (first cut used the closest failed margin; a −160 enrage wall with a coincidental near-miss on healing must teach nothing). Tested deterministically: same seed, progress 90 vs 0 → higher contested margin, ≤ deaths, ≥ kills.
3. **State deltas returned, not applied:** morale (kill +4 / wipe −2, died −1, saved +2), fatigue (+3, +1 extra on wipes — wipes grind), form ((rating − 5.5) × 0.8). The campaign layer (M5) owns `player_week_state` application.
4. **`persist()`** writes the fact rows (`pull`, `pull_participant` with role subquery, `pull_event`) and UPSERTS `guild_encounter_progress` (first_kill_at COALESCEd, set once). `pull_event.phase_id` is NULL for now (contract events carry phase_order; a phase-id map lands when the M4/M5 loader threads real ids). A synthesized `assigned_duty` check row summarizes duty outcomes when duties fired.
**Consequences:** the M3-005 harness drives `PullResolver.resolve` directly; M4's report reads `checks[]`/ratings/log verbatim; M5 applies the returned state deltas weekly. Schema note honored: pull uniqueness is (event, encounter, attempt_number) — callers increment attempts.

## ADR-0020 · 2026-07-10 · Balance harness: contract asserts, not golden numbers (M3-005)

**Decision:** `tools/harness.gd` sweeps every seeded encounter across gear multipliers (0.8→3.0, dense in the transition region) × N seeded pulls on a REAL generated campaign, reporting win rates + top wipe reasons and dumping per-pull CSV for the balance lab. `--assert-winrate LO HI` enforces the difficulty-via-margin contract as three SHAPE properties (not brittle absolute numbers): (1) the 60–80% band is REACHABLE on boss 1 at some gear step; (2) win rates are MONOTONE in gear (slack 0.06); (3) the curve SPANS decisive-wipe (≤25% undergeared) to one-shot (≥90% at next-tier gear). Wired into CI at `--pulls 100`. Also shipped `sim/resolution/pull_input_loader.gd` — the ONE DB→PullInput path (COALESCE selector override, avatar×player×spec×proficiency join, neutral state pre-M5, tuning.json merge); M4 must reuse it.
**Bug the harness caught on run #1:** the loader scaled gear but kept generation-time cap flags — a 3×-geared tank stayed "not uncrittable" forever, walling every deeper boss with tank_survival. Caps now recompute from scaled ilvl via `AvatarGen.CAP_ILVL_THRESHOLD` (M6-005 owns the real rule later).
**Balance-lab finding recorded, deliberately NOT tuned away:** Emberdeep bosses 2–4 are MECHANIC/learning walls, not gear walls (awareness-driven checks that gear cannot buy; win rates 16–29% even at 3× gear, rising with encounter_progress). Era-authentic progression shape; whether the wall heights feel right is a fun-gate/playtest question for M4, answered with this harness + the CSV in hand.

## ADR-0022 · 2026-07-11 · Intervention: the Fun Gate is not passed; MI blocks M5

**Context.** M4 shipped technically complete (117 tests, all gates green), but `guildmaster-intervention-and-realignment.md` challenged whether technical completion proves the *experience*. It does not. Reproduced and instrumented: the default first session is **32 pulls, 0 kills, 32 wipes**.

**Measured root cause (two compounding faults):**
1. **Content/start-state deadlock.** Boss demands were authored in M1-002 as explicitly "symbolic" numbers, never tied to real roster output. At the actual starting roster (avg ilvl 18.9, gear_score 132) the DPS lane produces 27.6 against Krogg's demand of 40; Tier-1 drops average **ilvl 31**. The entry boss demands roughly the gear it drops — no kill without loot, no loot without a kill.
2. **Conjunctive check aggregation** (found during this analysis, not in the original findings). The four checks are independent rolls that must *all* pass — a healthy raid at p=0.8 each still kills only ~41% of the time. And healing/mechanic failure are **already** modelled by the timeline as cascade/avoidable deaths, so the checks double-count them.

**Decisions (Panos, 2026-07-11):**
- **I-01/I-02 — Fix content AND aggregation.** New milestone **MI (Intervention & Fun Gate)**, which **blocks M5**. Encounter progression contracts per boss; retune so a *starting* roster kills Krogg in ~3–8 pulls after a real intervention; rework aggregation so DPS+tank drive kill-vs-wipe and soft lanes apply pressure. Harness extended to assert each boss against its own contract plus prep-leverage probes.
- **I-03 — Season = Tier (Model A).** One v1 expansion = two seasons, one per tier. Resolves the docs' contradiction; `content-and-dod`'s "14-week season across 2 tiers" bar was wrong and is corrected.
- **I-12 — Phase B-lite.** M5–M9 restaged as product gates: campaign/calendar/save → **Council-only** loot → basic treasury → **applicants-only** recruitment → one tier's objectives. Breadth (DKP//roll, deep economy, remaining channels, recovery valves, rival identity) moves to a new **MB** backlog, pulled in only after the week/season loop plays well.
- Contracts approved and scheduled: raid-night presentation (I-04), diagnostic hierarchy — "culprit" becomes internal shorthand (I-05), performance rating before M6 (I-06), involvement modes as a *contract now* to guide Phase-B UX (I-07), dual-language terminology (I-08).
- **I-10 (quirks/events in v1) deliberately NOT decided** — the doc's own guidance is to decide on playtest evidence after the Fun Gate.

**Consequence.** The Fun Gate is a **human verdict** (MI-010), scored against the card in `content-and-dod`. A weak score means tune/present/clarify — never "add more systems". No Phase-B ticket starts until MI-010 passes.

## ADR-0023 · 2026-07-11 · Gating vs pressure checks (MI-002)

**Decision.** Stage-3 checks split into two kinds. **GATING** (`dps`, `tank`) are rolled and alone decide kill vs wipe. **PRESSURE** (`healing`, `mechanic`) are never rolled and never gate a kill; they report whether the lane met its demand and exert their force through the **timeline** — a healing shortfall raises the effective severity of every death event (new `healing_deficit_lethality`), while low awareness already drives avoidable deaths. Deaths past the collapse threshold still wipe the raid, so soft-lane failure remains lethal *by killing bodies*, which is legible in the log.

**Why.** The old rule rolled all four independently and required all to pass. Two faults: (1) it capped even a healthy raid at ~41% (0.8⁴); (2) it **double-counted** — the timeline already punished low awareness (avoidable deaths) and thin healing (cascade deaths) via events, then the checks punished the same failures again. This was half the reason the default first session was 32 pulls / 0 kills.

**Measured effect (aggregation fix alone, no content changes):** Krogg 1%→8% at x1.0 gear and 55%→81% at x2.0; Vell 7%→31%, Slagbeast 3%→43%, Cinderlords 2%→26% at x2.0. Later bosses became reachable at all. 117/117 tests green; harness shape-asserts still PASS.

**Also added:** `pull.contributing_factors` — the coupled conditions that made the primary cause fatal (thin healing, low awareness, a non-crit-immune tank, missed duties, bodies lost). This is the groundwork for MI-005's diagnostic hierarchy: **primary cause ≠ culprit.**

**Consequence.** `wipe_reason` can now only be `tank_survival`, `raid_collapse` or `dps_enrage` — healing/mechanic can never be a *primary cause*, only a contributing factor. A near-margin wipe fixture must be built on a gating check (this broke one learning-arc test, which was correct and was updated, not weakened).

## ADR-0024 · 2026-07-11 · Encounter demands are anchored to the gear ceiling, not authored symbolically (MI-001)

**Decision.** Boss demands are no longer free-floating "symbolic" numbers to be tuned later. Every encounter now has a written **progression contract** — expected roster gear, intended win rate, dominant challenge, the player intervention that fixes it, and the seed values that produce it — in `docs/guildmaster-encounter-contracts.md`. That document is the source of truth: **retuning a boss without updating its contract is a bug.**

**The governing constraint — the gear ceiling.** A raider has 7 slots; starting gear averages ilvl 18.9 (`gear_score` 132) and every Tier-1 drop is ilvl 31. Therefore the **realistic in-tier gear band is x1.00 → x1.64.** Anything needing more than ~x1.65 is *unreachable content*. The balance harness swept to **x3.0** and reported healthy win rates at gear the player can never obtain — which is exactly how three of four bosses stayed uncompletable while CI passed green. `GEAR_SWEEP` is now clamped to the real band.

**Why.** The M1-002 encounter demands were authored before a roster generator existed, so nothing tied them to real output. Starting raid DPS is **27.6**; the entry boss demanded **40**. The tier's front door demanded roughly the gear it drops — a hard deadlock, and the other half of the 32-pulls / 0-kills first session.

**Retune (seed rows only — no engine code):** Krogg `24/32/38` · Vell `27/36/30` · Slagbeast `33/68/30` · Cinderlords `42/52/34` (`dps_check` / `healing_check` / `difficulty`).

**Measured effect.** Every boss lands in the 22–35% progression band at its intended gear (Krogg 40% at x1.00 — a *fresh* guild; Vell 29% at x1.12; Slagbeast 31% at x1.28; Cinderlords 22% at x1.42), and each is a wall at the previous boss's gear — so the tier now teaches gearing. `slice_smoke --seed 133742`: **32 pulls / 0 kills → 17 pulls / 4 kills (full tier).** No guild seed produces zero kills. The tank gate is verified as a real lever: **38.5% vs 0.5%** on crit-immunity alone (a 77× swing), which is the arc MI-003 builds on. 117/117 tests green; harness gate PASS.

**Consequence.** The old "**~60–80% win/pull** for matched progression" target in `guildmaster-resolution.md` is **superseded** — at 70%/pull a progression boss dies on pull 1–2, which is a farm feel and contradicts the learning arc's own "8%… 3%… KILL" language. **Progression = 22–35%/pull (kill in 3–8); farm = 65–90%.** MI-009 replaces the harness's single global band-assert on Boss 1 with **per-boss contract assertions** (progression band, farm band, dominant-failure identity), so a boss that only passes on unreachable gear is a *failing* boss.

## ADR-0025 · 2026-07-11 · The defense cap is a spec property, not a gear threshold (MI-003)

**Decision.** Crit-immunity is derived from the **tanking spec's own** `defense_cap_ilvl` (a `spec` seed column; 0 = cannot tank), not from one shared item-level threshold. `AvatarGen.derive_caps(avg_ilvl, role_slug, defense_cap_ilvl)` stays THE single caps rule (ADR-0021) and every path — generation and gear-scaled resolution loads — calls it. Seeded: **Bulwark 20 · Bastion 21 · Oakhide 27** (plate caps early; hide must badly over-gear).

**Why.** The tank gate is the strongest lever in the game — measured on Gatewarden Krogg at starting gear, a crit-immune main tank wins **38%** and a crittable one wins **0.5%**, a 77× swing that dwarfs every other prep decision (comp ~11 points, healer count ~4). But **the player could never get it wrong and never fix it.** `uncrittable` was `avg_ilvl >= 22` for every tank alike, and `gear_score` is just the sum of the same 7 slot item levels — so *crit-immune* was **identical to** *best-geared*, and `auto_lineup` picks tanks greedily by gear score. Across 10 seeds: 6 handed the player a correct main tank silently, 3 had no cappable tank at all (an unfixable 0.5% wall), and **0 contained a decision**. The game's best teaching moment was decided entirely by time, never by judgement.

**Consequence.** A tank can now out-gear the room and still be crittable, so **fielding the tank who is "worse" on paper is the right call** — and the player has to understand why. This is what makes Krogg's authored identity (the entry readiness gate, ADR-0024) reachable through the prep screen instead of through the loot table. An Oakhide is not a dead pick: he caps once the tier has fed him, which is a gearing goal.

**Also.** `data/migrations/0002_spec_defense_cap.sql`. The old caps test asserted the superseded rule and was rewritten, not weakened — it now proves the load-bearing claim directly: `derive_caps(24, "tank", 27)` is crittable while `derive_caps(21, "tank", 20)` is immune. **A better-geared tank can be the wrong tank.**

## ADR-0026 · 2026-07-11 · The first session is authored (MI-003)

**Decision.** Night One curates **exactly one thing** — the tank corps — into the shape that teaches: the best-geared tank is a hide-armoured bruiser who cannot be crit-immune, sitting above a plated tank who is. The other 24 raiders stay procedurally generated. The game's **own default lineup walks into the trap** (`auto_lineup` is greedy on `gear_score`), so no artificial benching is staged — the lesson is *"the default is a heuristic, not an answer."* Contract in `docs/guildmaster-first-session.md`, enforced by `tests/first_night_test.gd`, narrated by `tools/smoke/first_night_smoke.gd`.

**Why.** Random rosters do not teach: across 10 seeds, **zero** produced a first session containing a decision (see ADR-0025). The first ten minutes are the whole pitch — a player who does not diagnose, fix, and see the fix work has met a dice roller, not the game.

**The arc, measured (10/10 seeds).** Default lineup: **1–3% win**, dominant wipe `tank_survival`, and raid prep says so *before the pull* ("Main tank X is not uncrittable — spike-death risk"). Bench the star tank → a crit-immune tank inherits the duty → **21–46% win, a kill in 2.2–4.7 pulls.** On the demo seed: **3.3% → 40.7%, a kill in ~2.5 pulls.**

**Consequence.** Night One deliberately does **not** stack comp/healing/range flaws on top — one legible cause, one decision, or the player cannot tell which fix mattered. `game/demo_campaign.gd` is slice scaffolding: **M5-001's guild genesis must carry this contract forward**, or the game loses its opening. MI-010 (the human Fun Gate) scores this session.

## ADR-0027 · 2026-07-11 · The fight says how it ended; notability is derived (MI-004)

**Decision.** Two things, both in the engine, because the combat log is a thin renderer and the show's failures were not styling failures.

**1 — Every pull closes with its own `decisive` beat.** `Timeline._emit_closing_beat` appends a short human line naming how the fight ended (`boss_down` / `wipe_call`). **Why:** the verdict was computed *after* the timeline and **never written into the log**. A first-session tank-gate wipe read as four routine lines and then a verdict from nowhere — the decisive moment was not in the show at all, and no amount of colour could add it. `wipe_reason` remains a precise diagnostic string; it is far too long to be a beat and belongs on the card.

**2 — Notability is DERIVED from the event outcome, never stored** (`PullContracts.notability_for()`, tiers `routine / notable / critical / decisive`). A stored tier is a fact that can drift from the fact it describes. Every surface that renders events — the combat log, MI-005's why-view, a future replay — calls the same classifier, so they cannot disagree about what mattered. Unrecognised outcomes fall to `routine`: a new event type is texture until somebody tiers it, which fails quiet instead of crying wolf.

**Also.** Phase changes render as ruled banners titled with the phase's real name (`NightRunner` now hands the screen `phases[]`; events carry only `phase_order`). The wipe card shows `boss to N%` against the running best — **"CLOSEST YET"** — which is the "one more pull" line and the entire reason a raider stays. Pacing: Live (0.45s/beat, 1x–4x) or Instant, with skip-to-result.

**Deliberately NOT done: a live boss-health bar.** The engine does not model boss HP over time — it derives final progress from the DPS-check margin. A smoothly draining bar would be the feed **inventing a number the simulation never computed**, which is the exact class of failure this intervention exists to stop. Boss health is reported where it is real: as the outcome. A live bar requires the engine to model HP per phase first, and that is a ticket, not a UI tweak.

**Consequence / open issue.** A `tank_survival` wipe currently marks **nobody dead** — the tank check fails as a *check*, no death event fires, so `participants[].died` is false for all and the post-night report can show 0 deaths on a wipe caused by the tank dying. The log now handles this honestly (the beat says "cannot hold it", not "is cut down"; the raid counter drops to 0 because a wipe *is* a wipe), but the incoherence is real and is assigned to **MI-005**: either the tank gate emits a real `tank_death` event, or the report stops implying deaths it does not have.

## ADR-0028 · 2026-07-12 · A dominant check is not a guilty person (MI-005)

**Decision.** Player-facing failure is a **hierarchy**, never one sentence: **primary cause** (the gate that failed) → **contributing factors** (the coupled conditions that made it fatal) → **key moment** (a person, *only* when directly attributable — usually nobody) → **recommendation** (the lever to pull) → **recurrence** ("the same wall, not bad luck"). `sim/resolution/diagnosis.gd` is the pure module; `docs/guildmaster-diagnostics.md` is the contract. `wipe_reason` survives as **internal shorthand** — the numeric string for logs, tests and the balance lab — and is no longer shown to the player anywhere.

**Why.** "Every wipe names a culprit" is half a pillar. Failures here are deliberately COUPLED (low awareness → avoidable damage → healing strain → tank drops → collapse), so the dominant check is not a root cause and certainly not a guilty person. A UI that points at a name teaches the player to bench their lowest-rated raider instead of fixing the system.

**🔒 THE ANTI-SCAPEGOAT RULE — a raider may be named, or rated down, ONLY for a failure they authored** (they were rolled against something they control). This is a **rating** rule, not a copy rule: the player does not read the design doc, they read the ratings table, and a tank sitting at the bottom of it IS the game telling them to bench him.

**Two live bugs, the same shape, neither cosmetic:**
1. **`tank_overwhelmed` did not exist.** The stage-3 tank check is a *lane* check — it fails with no death event anywhere in the timeline. A `tank_survival` wipe left the tank standing and the report showed **0 deaths on a wipe caused by the tank dying** (surfaced by MI-004). He falls now — as his own outcome, with a **0.0** rating delta, because the guildmaster fielded him uncapped; he did not author it. Measured: an out-damaged tank went from **floored at 1.0/10** to **5.3/10, mid-table**.
2. **A cascade death was billed as an avoidable one.** The resolution doc always called `cascade_death` "death, *not own fault*", but the engine emitted a plain `death` — so the raider the healing shortfall happened to catch was docked the same **−2.0** as somebody who stood in the fire, and could be named as the "key moment". Now its own outcome, **0.0**.

Standing in the fire (`death`) and dropping a duty you were handed (`duty_fail`) still cost **−2.0**. The point is not that nothing is ever anyone's fault.

**Also fixed: recurrence never worked.** `top_wipe_reasons` tallied the raw `wipe_reason`, which embeds margins and probabilities — so every wipe hashed unique, every count came out as 1, and the one sentence that tells a player *"you are not unlucky, you are stuck"* could never appear. Wipes group on the **primary cause** now.

**Consequence.** **Balance is untouched** — both deaths are emitted *after* the verdict, so the checks and collapse fraction that decided the pull never see them. The harness reports identical win rates to the point (40 / 21 / 11 / 5 % at starting gear). This closes an incoherence; it does not open a new failure path.

## ADR-0029 · 2026-07-12 · Gate 1 passed — the raid night is fun (MI-010)

**Decision.** **Phase A is closed.** The human Fun Gate — the one verdict in this project that no test suite can give — passed on 2026-07-12.

> *"It seems solid, hard enough but doable, I feel it just about right."* — Panos

**Why it matters.** Twenty-four hours earlier the same build resolved **32 pulls, 0 kills, 32 wipes**, and every automated gate was green while it did so. That contradiction is what milestone **MI** existed to resolve: the tier was uncompletable (ADR-0024), the checks were conjunctive and capped a healthy raid at ~41% (ADR-0023), the first session contained no decision (ADR-0025/0026), the log had no ending (ADR-0027), and the report blamed raiders for the guildmaster's own failures (ADR-0028).

**The verdict agrees with the instrumentation.** The encounter contracts target **22–35% win/pull** on progression content — a kill in 3–8 pulls — and Night One measures **3.3% → 40.7%** across the readiness fix. "Hard enough but doable" is that band, felt rather than computed. Keeping both a human gate and a balance harness only pays off at the moment they agree; this is that moment.

**What the verdict does NOT cover.** It was given by the designer, an expert player. It says nothing about *"can a non-MMO player act on the UI's warnings alone?"* — that scorecard line remains open and belongs to **MI-008** (terminology). Do not read this ADR as clearing it.

**Consequence.** MI's remaining tickets (MI-006…MI-009, MI-011, MI-012) still land before M5, per `guildmaster-backlog.md`. **The first thing to protect is the thing just blessed:** MI-009 replaces the harness's single global band-assert with **per-boss contract assertions**, so the difficulty Panos just approved cannot silently regress. A green harness that permits an unfun game is the precise failure this milestone was created to prevent — and it must not be allowed to recur.

## ADR-0030 · 2026-07-12 · The harness asserts contracts, and healers stop being a trap (MI-009)

**Decision.** Two things, and the second only exists because the first found it.

**1 — Per-boss contracts, as DATA.** `data/seeds/encounter_contract.csv` (+ migration `0003`) is the machine-readable half of `guildmaster-encounter-contracts.md`: expected gear, progression band, farm band, dominant failure, and a **signature lever**. The harness asserts every boss against **its own row**, `seed_check` fails a boss with no contract, and CI gates on both. "Retuning a boss without updating its contract is a bug" was a convention; conventions do not fail builds. Now it does. Contracts are measured against a **PREPARED** raid (crit-immune main tank, duties on the best hands) — otherwise the numbers grade the roster lottery instead of the boss.

**Why.** The old harness asserted ONE global band on boss 1 and swept gear to x3.0. It passed green while three of four bosses sat at a **0% win rate** on gear the player could never assemble. A green harness that permits an unplayable game is the precise failure milestone MI exists to prevent.

**2 — PREP-LEVERAGE PROBES, and what they caught.** Gear was the only thing the harness ever varied, so it could not tell whether raid prep was **tactics or administration**. The probes hold seed/roster/gear fixed and vary ONE decision. They immediately found that **healers were a trap**: more healers made the raid worse on *every* boss — **including The Slagbeast, whose entire identity is the healing wall.** The optimal play was to strip healers and stack DPS.

Three faults conspired: Slagbeast's healing demand was **unreachable** (77 against a lane that tops out at 46 — a locked door, not a wall); its tank check was **saturated** (p≈0.94), so the healing that feeds tank survival was thrown away; and the DPS sacrificed came straight off `dps_enrage`, the only gate deciding the fight. **Fix:** demands made *closable*; `tank_healing_share` 0.35 → **0.50** so healers protect a gate that binds; `healing_deficit_lethality` 0.6 → **1.0** plus two more cascade beats on Slagbeast, so thin healing actually **bleeds bodies**.

**The Fun Gate verdict (ADR-0029) was held as a hard constraint** — the default-comp win rate had to land where Panos played it, and it does (within 2pp on every boss: 40 / 34 / 32 / 23). Night One is intact (5.3% → 44%, a kill in ~2.3 pulls). **The gradient changed; the feel did not.**

**🔒 "More healers is always better" is NOT the rule.** Over-healing a DPS race *should* cost you (−13.5pp on Cinderlords) — that opportunity cost is what makes comp a decision rather than a checklist. What a lever may never do is fail on **its own** boss. Measured: krogg→tank_cap **+40.0**, vell→duties **+5.5**, slagbeast→healers **+10.0**, cinderlords→consumables **+6.0**. Every lever is a real decision somewhere; every boss answers to its own.

**Consequence / the lesson.** The harness's own first draft printed *"ok: 'healers' is a real decision, 17pp"* — because it compared **|delta|**. It measured the magnitude of a lever that was pointing the wrong way. **Never measure a lever's strength without its sign**; an inverted control is worse than a dead one, because the game is actively teaching the opposite of its design. Slagbeast's dominant failure is `tank_survival` and that is *correct*: a healing wall kills by running the healers dry until the tank falls. The diagnosis (ADR-0028) keeps it distinct from Krogg's readiness gate via its contributing factor and recommendation.

## ADR-0031 · 2026-07-12 · Jargon is optional, never load-bearing (MI-008)

**Decision.** Dual-language, everywhere the player reads: **plain-language CONSEQUENCE first, the ACTION always, the MMO term LAST, in parentheses.** Terms are **kept** — this is a game about old-school raid guilds and stripping the vocabulary would strip the fantasy — but they are never **load-bearing**: a player who ignores every parenthesis must still be able to act. Definitions live in `data/seeds/glossary.json` (content as data, the `tuning.json` pattern); `sim/core/glossary.gd` reads them; the prep screen hangs tooltips off a `term` key. Contract: `docs/guildmaster-terminology.md`.

**Why this is not a cosmetic ticket.** The single string the **entire first session** hangs on read: *"Main tank Shadowwhisper is not uncrittable — spike-death risk."* Two terms a non-raider cannot parse, **no consequence, and no action.** MI-003 built the whole opening around the player reading that sentence, understanding it, and benching their best-geared tank *because* of it. If it does not land, the diagnose → fix → succeed arc collapses — for exactly the player this game is trying to reach. It now names the consequence (*"one unlucky spike will kill him outright and end the pull, and no amount of healing prevents it"*), the fix, and the counter-intuitive part out loud (*"even if their gear score is lower"*).

**Enforced, not aspirational.** `tests/terminology_test.gd` makes the rule mechanical: every warning must contain an **action verb** (a warning with no action is an observation); no jargon may appear **before** a parenthesis (naked, unexplained); every tagged term must exist in the glossary; and no glossary entry may "explain" a term with itself. **The old tank warning fails two of these outright** — which is the point.

**Also.** The same rule applies *after* the pull: it would be incoherent to make raid prep readable and leave the wipe report in engine-speak. The diagnosis (ADR-0028) now says *"your healers could not keep up with the damage"* rather than *"healing lane fell 5.6 short"*, and *"the boss outlasted you: its damage became unsurvivable while it still had health left"* rather than *"enrage"*. Tests and smokes that matched the literal string `"not uncrittable"` were repointed at the **structured `term` field** — a test that sniffs for jargon would have blocked the very fix that removes it.

**Consequence — and what this does NOT claim.** The Fun Gate (ADR-0029) was passed by an **expert** MMO player, so the scorecard line *"can a non-MMO player act on the warnings alone?"* has still **never been tested on an actual non-MMO player.** This ticket makes that outcome *plausible*; it does not make it *proven*. The only thing that proves it is putting Night One in front of somebody who has never raided and watching whether they bench the tank. **That line remains open on the Gate 1 scorecard.**

## ADR-0032 · 2026-07-12 · A rating is what you did with what you were given (MI-006)

**Decision.** The 1–10 performance rating measures **how well a raider fulfilled their role and their assignments, relative to the kit, gear and situation available to them.** It is **not** raw output. `expected` is derived from the raider's **own** ceiling, which is what makes the number fair across roles and gear levels with no special-casing. Contract: `docs/guildmaster-rating.md`; the five validation scenarios and the three questions are `tests/rating_contract_test.gd`.

**Why the principle is load-bearing.** A rating that just re-reported raw damage would just re-report **gear score** — and loot awarded on that evidence becomes a **feedback loop that eats itself**: the best-geared raider "earns" the loot that keeps him best-geared. The rating exists to break that loop, and it must be locked **before** M6's Council starts treating it as evidence.

**The three questions, answered.**
1. **Can a duty failure be double-counted through event + death + rating? NO — a failure is charged exactly once, to whoever authored it.** The assignee takes the `duty_fail` delta; the raider their miss *kills* takes **no rating hit at all** (the timeline kills the victim but targets the event at the assignee). And a dead raider **keeps their own contribution** — death removes them from the lane SUMS, never from their own ratio — so dying costs the −2 and nothing more. Both asserted as **exactly 2**, not "roughly bad".
2. **Can an undergeared player earn a 9 by overperforming? YES, by design** — a raider in rags who outplays his gear outranks a decked-out raider coasting.
3. **Can a highly geared player rate poorly despite high raw output? YES** — the test asserts his `raw_contribution` is genuinely the *higher* of the two **and** his rating the *lower*.

**Every rating now carries a plain-language breakdown** (`rating_factors` + `rating_summary`; night-grain "why" in the report). A number nobody can argue with is not evidence, it is a vibe. Crucially the breakdown **shows the deaths that were NOT the raider's fault and says so** — *"was out-damaged, not out-played — no fault of his"* — because the player does not read the design doc, they read the **ratings table**, and a corpse beside a number is how a guildmaster benches the wrong raider (the scapegoat trap, ADR-0028).

**Consequence.** Locking this contract required **no change to the rating maths** — the engine was already correct. What it lacked was a specification and an explanation. Both now exist, and eleven tests hold the next person to them. The night-level "why" deliberately omits the output judgement: a per-pull verdict does not sum, and *"about what their gear should produce, eight times"* tells a guildmaster nothing.

## ADR-0033 · 2026-07-12 · Involvement changes who authors the inputs, never how the sim resolves them (MI-007)

**Decision.** Manual / Assisted / Instant, **per domain** (Lineup, Assignments, Pulls, Loot, Weekly plan, Recruitment), stored in `GAME_CONFIG` (six `involvement_*` columns initialised from the planned `involvement_default`; three genesis presets — Full Control / Guided / Hands-Off — are UI sugar that write all six; "Custom" is derived, never stored). A `decided_by` audit column (`'player'|'assistant'`, CHECK reserving room for officer slugs in v1.1) lands on `RAID_LINEUP · RAID_ASSIGNMENT · WEEK_ACTION · LOOT_DROP` **at M5-001**. **Contract only** — implementation is M9-005 + the Phase-B screens. Full contract: `docs/guildmaster-involvement.md`.

**The one principle.** *Involvement changes who authors the inputs, never how the sim resolves them, and never what information exists.* Determinism is untouched (delegation decides who fills the lineup; the resolver runs on those inputs identically); automation moves *where* a decision is shown (screen → handoff card → report), never *whether* it exists.

**The load-bearing call — one fallible officer, on purpose.** In v1 there is ONE assistant and it uses the exact heuristics the game's own warnings critique — `auto_lineup()` stays greedy-by-gear-score; Assisted prefills it, Instant commits it, Manual can summon it. **No smarter optimiser hides behind Instant.** Night One's thesis is "the biggest number is not the right call"; a smart Instant would silently append "…unless you stop looking, in which case the computer secretly knows better," poisoning the player's mental model of every prefill. Delegation = trust in a legible, imperfect officer, not access to a hidden better answer. Bonus: one heuristic = one pure code path, one test surface, no divergence between what the screen suggests and what the delegate does. Delegation quality as a **recruitable officer stat** is v1.1 (the `decided_by` CHECK already reserves it — no migration needed).

**Night One survives any settings choice (the PIN).** The first raid night of a new campaign forces Lineup/Assignments/Pulls/Loot to **Assisted** regardless of settings — *"walk the floor once; from next week your officers can take over."* A genesis-time Instant choice takes effect from week two. Defence in depth: even without the PIN the fallible officer does not pre-solve the lesson — it fields the crittable default, wipes on `tank_survival`, hits the recurrence line, and the printed recommendation is the fix. The PIN exists so the player learns it the *good* way (prep screen), not just the systemic way (report).

**Loot pillar squared.** "Loot is a leadership decision" was never "loot is a per-drop click" — it is choosing and owning the **culture**. DKP//roll already run themselves (loot doc: "the low-micro option"); their Instant is their native form; consequences (morale/loyalty/fairness/ego/drama) land on the guildmaster identically regardless of `decided_by`. **Loot Council is clamped to Assisted in v1** (pre-sorted + recommended, but you press the button); the auto-steward is v1.1.

**Consequence.** Phase-B screens (M5–M9) build their three modes from the first version — never "manual now, automation later." Functional in v1: Lineup/Assignments/Pulls (engine has both ends), Weekly plan (advisor function serves Assisted-prefill + Instant-commit), Loot (M/A for Council, all three for DKP//roll). Contract-only in v1: Recruitment-Instant, Council-on-Instant. The v1 manual fence is unchanged — strategy/lineup/between-pull swaps/wipe calls; **no mid-pull directive injection in any mode** (that is v1.1, per the resolution doc's "layer later").

**Method note.** The contract was triangulated from three independent designs (FM-authentic / minimal-v1 / teaching-and-trust); all three converged on the spine unprompted, and the divergences (chiefly Night-One protection) were resolved toward the most robust option (the PIN, from the teaching lens).

## ADR-0035 · 2026-07-12 · The weekly turn loop — a save-backed day cursor (M5-002)

**Decision.** The campaign advances through a week with `TurnLoop.advance(db, rng)` — an FM-style "continue" that ticks recovery across empty days and stops ON the next scheduled event (raid / dungeon / rest / social) for the player to resolve; `complete_event()` frees it to advance again. Weeks roll automatically until the season's last week, where the loop stops for grading (M9). New modules: `sim/campaign/{calendar,turn_loop,week_state}.gd`.

**Three small decisions worth recording:**

1. **A day cursor on the save, not derived state.** Migration `0005` adds `GAME_STATE.current_day` (0 = planning; 1–7 = the day reached). The alternative — deriving position purely from `CALENDAR_EVENT.status` — cannot tell which empty days have already been ticked, so recovery would double-apply. Time stays represented through `GAME_STATE + WEEK + CALENDAR_EVENT`; no wall clock.

2. **Lazy week-state snapshot keeps genesis untouched.** `PLAYER_WEEK_STATE` rows are created on first need (`WeekState.ensure`), carrying the prior week's morale/fatigue/form forward (defaults for week 1). This let M5-002 be **purely additive** — the just-shipped M5-001 genesis was not re-touched, and its week-1 raid event is picked up by the loop naturally. (Consequence: genesis's week 1 has only the raid; weeks 2+ get the default raid+rest calendar. Harmless — week 1 simply has more empty days.)

3. **The season boundary stops, it does not loop.** At `week_number == expansion.season_length_weeks` the loop returns `season_complete` and sets phase `grade` rather than creating a week 15 — the honest boundary, since grading / sacking / the roll into Season 2 (Tier 2) are M9 and MC-001.

**Deferred (noted, not done here):** applying the raid night's morale/fatigue/form **state_deltas** to `PLAYER_WEEK_STATE` — the resolver returns them but nothing writes them yet (the M4 "known gap"). M5-002 gives empty-day *recovery*; the raid-night *cost* is a downstream resolve step (M5-004 / a resolve phase).

**Verified:** 178/178 tests, boot, seed_check, and the turn-loop / genesis / first-night / slice smokes all green; the loop is deterministic (same seed → identical transcript) and fully save-backed (progression re-read from the DB, never UI-held). **Not verified locally:** gdformat/gdlint — still blocked by the dev machine's Windows Application Control policy (ADR-0034); CI runs them on Linux.

## ADR-0036 · 2026-07-12 · Availability is a window gate + a volatility fog; the two "can't raid" walls become choices (M5-003)

**Decision.** Raider availability is rolled per event and written to `EVENT_AVAILABILITY`, so the lineup is drawn from who actually showed. Two gates, and the reason says which: a **WINDOW** gate (structural — a Shift Worker is simply not free in the evening slot; no roll) then a **VOLATILITY** roll (the fog — even in-window, a spiky raider whose life situation is demanding no-shows; `show_rate = base_rate − effective_volatility × scale`). Deterministic: a per-player substream off an event-scoped `RngStream`. Reasons are plain-language (MI-008) and present on every unavailable row. New: `sim/campaign/availability.gd`, `sim/raid_prep/prep_decisions.gd`, migration `0006`.

**The two "can't raid tonight" walls become choices** (raid-prep doc): **undermanned** → `run_short` (proceed weaker) or `cancel`; **undergeared** → a per-boss readiness preview (`✓ Ready · ~ Tight · ⚠ Undergeared · ✗ Heavily`, graded from lineup gear ÷ each boss's `expected_gear` in the MI-009 contract) → `downshift` (attempt only the gearable front — "farm the front, gear for the back") or `convert_to_dungeon`. Convert is a `CALENDAR_EVENT` type change; downshift records a boss subset (the only new state — `calendar_event.target_boss_subset`, NULL = whole raid, read by the night runner later). All four mutate the event, never a parallel state; all are plan-time (guarded to a still-`scheduled` event).

**Reviewed adversarially before commit.** A 3-lens finder → adversarial-verify workflow raised 8 findings and confirmed 0 as live bugs — but three were genuine LATENT fragilities worth hardening before M5-004/UI wires callers: (1) the decisions had no status guard (could rewrite a completed raid) → now refuse on a non-`scheduled` event; (2) `roll_for_event` wasn't idempotent (a re-roll hit the PK and desynced the summary) → now delete-first, re-runnable; (3) a NULL `life_situation` produced a `"<null>"` reason (unreachable — RosterGen always assigns one — but the LEFT JOIN exists to tolerate it) → now coerced to "free every slot". Each is covered by a regression test.

**Tuning observation (flagged, not changed).** With `base_rate 0.9 / volatility_scale 0.004` and the seeded roster, ~14 of 20 are available for the default evening raid — chronically undermanned. That is arguably working-as-designed (bench depth must matter, and undermanning is the whole point of the decision surface), and it is fully tunable, but it is on the punishing side and is exactly the kind of number the non-MMO playtest should judge.

**Verified:** 192/192 tests, boot, seed_check, availability smoke, and lint/format clean (via `python -m gdtoolkit.*`, since Smart App Control blocks the shims).

## ADR-0037 · 2026-07-12 · The five weekly lanes — bounded, audited, atomic (M5-004)

**Decision.** The between-nights lanes resolve through `ActionResolver` — a light version of the raid resolver: roll the relevant attributes against a lane difficulty → a **bounded** output (`quality = 0.5 + (inputs − difficulty)/spread ± band`, lerped across the seed row's `output_range`, floor above zero — **no feel-bad weeks**) → write **existing** model fields. Nine actions across the 5 lanes live in `data/seeds/action_type.csv` (content as data), authored **directly from the between-nights doc's own action table** — because M1's "seed starter kit" never actually authored `ACTION_TYPE` rows (the same class of gap as MC-001). Every applied action writes exactly one `WEEK_ACTION` audit row stamped with `decided_by` (ADR-0033), Supply mutations write `TREASURY_LEDGER` rows, and the **weekly time budget is a hard wall** (`action.weekly_time_budget`) — "time is scarce" made literal. **Deferred, per the doc:** coach (needs Mentor/RELATIONSHIP depth — M10), recruit/scout (M8), dungeon **gear drops** + minor skill XP from runs (M6-005 owns equip-on-award and the Marks vendor), professions (v1.1). Marks satisfy the Gearing acceptance today.

**Atomicity, from review.** The adversarial review ran degraded (session limits killed 8 of 9 agents), so the six findings its one surviving finder (SQL/atomicity lens) raised were verified **by hand** — and most were real, if latent. **Verified:** 208/208 tests, boot, seed_check, the action-resolver smoke (all 5 lanes, budget wall, deterministic) and the slice smoke (untouched: 18 pulls / 4 kills). Lint + format clean via `python -m gdtoolkit.*`.

## ADR-0042 · 2026-07-19 · The bench has a cost — marginal, ego-scaled, atomic (M5-007)

**Decision.** Repeated benching of AVAILABLE raiders now charges morale and current loyalty at week roll, scaled by ego — the raid-prep doc's promise, closing the explicit placeholder ADR-0038 left. One module (`BenchCost`) owns the streak walk, the pricing and the application; the digest renders the very function the roll applies, so the reported and charged numbers cannot diverge. Price: `per_night × streak × (0.5 + ego/100)` past the streak threshold (tuning `bench.*`); morale lands in the NEW week's snapshot (the week opens soured), loyalty hits `loyalty_current` only — baseline untouched, per the conventions.
